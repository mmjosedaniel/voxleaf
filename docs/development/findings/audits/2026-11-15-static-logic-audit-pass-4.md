### VF-0069 — Sustainability conclusion after rejected replay

The official replay concatenates elapsed generation durations and inserts both units at each batch completion. By inspection, suppose the first two complete batches each take two seconds and each contain two 15-second units. The first pair starts playback with 30 seconds. Two seconds later, accepting even the first unit of the next pair raises the buffered duration from 28 to 43 seconds and trips the 40-second ceiling. The simulator does not model waiting for capacity before dispatch on this timeline. The official runner catches the error and returns `playback-invalid` with an all-zero playback record. The example uses durations inside the declared 8–20 second unit limits. [Frozen replay policy](../../../../benchmarks/tts/profile-v4.json#L254), [arrival construction](../../../../services/tts/benchmarks/batch_official.py#L676), [replay bound](../../../../services/tts/benchmarks/batch_playback.py#L101), [zero record](../../../../services/tts/benchmarks/batch_official.py#L707).

The deriver copies the failure code but evaluates the zero-valued buffering and retention fields as successful measurements. With enough measured media, completed calls, low aggregate RTF, passing cancellation proof and the other audits passing, it emits `schedulingSustainability.outcome: pass`. The inherited schema accepts zero for these fields and the conclusion validator does not require a successful playback simulation. A focused check should follow a complete over-capacity arrival sequence through the v14 result and verify the conclusion, along with a valid bounded replay. [Retention audit](../../../../services/tts/benchmarks/batch_result.py#L348), [scheduling predicates](../../../../services/tts/benchmarks/batch_result.py#L403), [schema bounds](../../../../benchmarks/tts/schemas/short-segment-batch-raw-v4.schema.json#L498), [conclusion validator](../../../../services/tts/benchmarks/v4_authority.py#L613).

### VF-0070 — CPU qualification without batch-level attribution

The frozen qualification rule requires a memory stop on the first attempt of a full-GPU batch-two call. The official monitor can also latch a reserve breach during its final sample after the measured calls and cancellation trials have finished. The result has one overall memory-stop code and one total of failed measured attempts. For an otherwise valid, closed result with an independent generation failure and a final-sample `vram-reserve-exhausted`, the resulting code and total can satisfy CPU admission together. The checker requires 12 measured two-unit call rows, 24 unit rows and a positive failed-attempt total. It does not establish which call failed from that stop. The exact commit and worktree digest checks preserve file identity while leaving this attribution unresolved. [Qualification rule](../../../../benchmarks/tts/profile-v4.json#L267), [post-run sample order](../../../../services/tts/benchmarks/batch_official.py#L1136), [stop assignment](../../../../services/tts/benchmarks/batch_official.py#L367), [failed-attempt total](../../../../services/tts/benchmarks/batch_result.py#L293), [CPU admission](../../../../services/tts/benchmarks/v14_authority.py#L279).

The existing qualification test independently supplies the memory code and failed-attempt count. The earlier decision to stop an incomplete measurement before publishing any session remains applicable. To distinguish this case, hold version, exact commit and cleanup constant and compare an unrelated failure plus final-sample stop with an explicitly attributed qualifying attempt. [Version-bound fixture](../../../../services/tts/tests/test_benchmark_v14_authority.py#L136), [U11 early-stop decision](../../../plans/completed/five-pass-audit-revalidation-and-corrections.md#L858).

### VF-0071 — Cold-load run identity

The official command writes `raw.json` and `loads.json` separately. Raw carries the execution and authority identities. Each load row contains its index, load time and cleanup time. The derivation command reads both from the selected directory. The raw validator checks its own authority and order, and the load validator checks five ordered indexes and time bounds. Neither input carries a pairing identifier or digest that the deriver compares across them. If a local reprocessing step mixes two runs, the current validation can emit a cold-load result for the wrong execution. [Load row producer](../../../../services/tts/benchmarks/batch_official.py#L1112), [session writes](../../../../services/tts/benchmarks/batch_cli.py#L326), [derivation input](../../../../services/tts/benchmarks/batch_result_cli.py#L100), [raw validation](../../../../services/tts/benchmarks/batch_result.py#L164), [load validation](../../../../services/tts/benchmarks/batch_result.py#L74).

For example, the same valid raw data paired with five 61-second observations or five 30-second observations gives a different cold-load p95. Both timings fit the load input shape. If the other standard gates pass, the first pairing fails the cold-load gate and the second passes it. This scenario depends on file mixing. The ordinary writer itself obtains both inputs from one execution. [p95 and gate](../../../../services/tts/benchmarks/batch_result.py#L294), [cold-load limit](../../../../services/tts/benchmarks/batch_result.py#L376).
