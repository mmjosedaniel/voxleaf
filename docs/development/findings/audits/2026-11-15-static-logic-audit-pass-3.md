### VF-0066 — Playback rate change during refill

After an involuntary underrun at 1.00×, assume 45 seconds of new source audio are queued, the range is incomplete and the slower-rate worklet is cold. The speed control allows playback rate changes during buffering. Selecting 0.75× yields 60 playable seconds and moves the scheduler to `playing`. The player waits for the worklet before starting the next unit. [Speed control](../../../../apps/desktop/src/tts/ProductNarrationControls.tsx#L205), [duration calculation](../../../../apps/desktop/src/tts/adaptive-buffer-scheduler.ts#L957), [refill admission](../../../../apps/desktop/src/tts/adaptive-buffer-scheduler.ts#L1081), [backend readiness](../../../../apps/desktop/src/tts/playback-backends/web-audio-pcm-playback.ts#L108).

If the listener returns to 1.00× while the worklet is still pending, the scheduler recomputes the duration and then returns early because previous playback had already committed. The later publication synchronizes the player. The direct backend is ready, and the player can start the pending unit with only 45 playable seconds if the queue remains at that depth. The one-minute rule applies here because narration remains incomplete. Existing fixed-rate refill and pending-worklet Pause assertions exercise separate sequences. A discriminating check would delay worklet preparation through the second speed change and observe the device start boundary and its buffered duration. [Early return](../../../../apps/desktop/src/tts/adaptive-buffer-scheduler.ts#L1067), [rate change publication](../../../../apps/desktop/src/tts/product-narration-coordinator.ts#L758), [snapshot synchronization](../../../../apps/desktop/src/tts/product-narration-coordinator.ts#L2604), [device admission](../../../../apps/desktop/src/tts/pcm-playback.ts#L219), [refill requirement](../../../architecture/adaptive-buffer-authority-v1.md#low-water-and-exhaustion), [existing refill control](../../../../apps/desktop/src/tts/pcm-playback.test.ts#L2137).

### VF-0067 — Installer identity in the ordinary journey

The official journey checks that the installer exists, launches it, and completes the installed-app checks. It first captures the installer size and SHA-256 after reacquisition, using the same path. A rebuild may replace that path after installation has finished. The resulting receipt then pairs the replacement installer's digest with the executable and behavior observed from the first installer. The attachment validator matches the receipt's installer to the target and checks the installed executable's fields independently. A receipt that already contains the replacement digest can therefore supply the ordinary journey observation for that replacement when the other gates also pass. [Journey entry](../../../../apps/desktop/scripts/ordinary-chatterbox-release-host.mjs#L1131), [installer launch](../../../../apps/desktop/scripts/ordinary-chatterbox-release-host.mjs#L1174), [receipt timing](../../../../apps/desktop/scripts/ordinary-chatterbox-release-host.mjs#L1373), [receipt digest](../../../../apps/desktop/scripts/ordinary-chatterbox-release-host.mjs#L330), [attachment validator](../../../../apps/desktop/scripts/windows-release.mjs#L416), [hash-bound decision](../../../architecture/decisions/ADR-0050-promote-ordinary-chatterbox-acquisition-and-retire-validation-overlay.md#context).

The identity of the installed executable remains a separate observation by design. The lifecycle runner already takes a pre-run installer identity and checks it after cleanup. The corresponding ordinary case needs a controlled replacement after installation and verification of what digest the receipt attributes to the installed journey. [Installed identity contract](../../../architecture/mvp-release-authority-v2.md#current-ordinary-artifact-evidence), [lifecycle start](../../../../scripts/test-windows-package-lifecycle.ps1#L58), [lifecycle drift check](../../../../scripts/test-windows-package-lifecycle.ps1#L433).

### VF-0068 — Package authority during receipt attachment

The documented attach branch reuses the existing installer, executable and their matching receipts. The Node evidence command validates current checkout inputs and hashes the four authority documents again. Its Piper check compares the current tracked manifest to the current distribution copy. If both manifest files change while the existing installer and executable stay in place, that comparison can pass. Even a format-only change to both copies can change the raw manifest digest while preserving the parsed manifest. The final write checks artifact hashes and the previous antivirus observation, so the attachment can overwrite the earlier build authority for the same artifacts. [Attach instructions](../../setup.md#build-the-m011-windows-package), [attach branch](../../../../scripts/build-windows-release.ps1#L152), [manifest comparison](../../../../apps/desktop/scripts/windows-release.mjs#L351), [authority fields](../../../../apps/desktop/scripts/windows-release.mjs#L593), [prior evidence and write](../../../../apps/desktop/scripts/windows-release.mjs#L764).

This sequence can occur with two valid receipts and no installer replacement. The historical layout runner illustrates how the evidence field is consumed. It compares it with the verified Piper manifest next to the executable and rejects a mismatch with `desktop-piper-identity`. The existing attachment assertions cover Defender observation preservation and live executable drift. A follow-up should vary only the authority inputs, verify that the earlier authority remains bound or the write is rejected, and then check normal attachment with unchanged inputs. [Historical tooling scope](../../../plans/completed/documentation-consistency-and-historical-tooling.md#L48), [packaged manifest comparison](../../../../apps/desktop/scripts/tts-adapter-layout-host.mjs#L1450), [existing attachment assertions](../../../../apps/desktop/scripts/windows-release.node-test.mjs#L1338).
